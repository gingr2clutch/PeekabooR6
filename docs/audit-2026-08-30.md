## 1. Correctness

### 1.1 Sequential query waterfalls on the three highest-traffic pages — MEDIUM
`app/page.tsx:19-23`, `app/maps/[slug]/page.tsx:59-119`, `app/peeks/[slug]/page.tsx`

The homepage awaits 4 queries one after another; the map page 7; the peek page 6.
None uses `Promise.all`, though `/gadgets` does. Each query waits for the one
before it despite having no dependency on it — `getHomeStats()` does not need
`getMaps()` to finish.

**Breaks:** nothing functionally, but it is dead server time added to TTFB on
every request, which is LCP on an SEO-dependent site. Filed under correctness
rather than performance because the sequencing is unintentional, not a
trade-off.

**Fix:** small. Group the independent ones into `Promise.all`, exactly as
`/gadgets` already does. The map page needs care: `floors` genuinely depends on
`map`, and `topPeek`/`rankedPeeks` depend on `floorIds`.

### 1.2 Five Supabase calls discard the `error` field — SMALL
`app/admin/(authed)/peeks/upload-actions.ts:42`, `app/admin/(authed)/gadgets/actions.ts:34`,
`app/admin/(authed)/gadgets/[site]/upload-actions.ts:29`, `app/account/actions.ts:25`, `:74`

Written as `const { data } = await …`, so a failed query is indistinguishable
from an empty result. In the gadget cases this feeds `revalidatePath`, so a
failure silently revalidates nothing and the admin sees a stale list with no
error.

**Fix:** small. Destructure `error` and handle it. The rest of `lib/db.ts` is
consistent about this — 26 of 27 queries use `if (error) throw error`.

### 1.3 `getGadgetSiteOptions` is unbounded — SMALL
`lib/db.ts`

Selects every published `gadget_sites` row with no `.limit()`, then filters
client-side by map. Fine at 51 rows; PostgREST caps at 1000 by default, so it
degrades silently rather than erroring if the table grows past that.

**Fix:** small. Not urgent at current scale.

### 1.4 Things I checked that are fine

- **Hash anchors all resolve.** `#vote` and `#submit`/`#submit-gadget` all have
  matching ids. The `#submit` bug is fixed.
- **No dead internal hrefs.** Every `href="/…"` maps to a real route.
- **Floor pages are crawlable.** I suspected an SEO regression because
  `FloorPeekList` is orphaned (see 4.1) and `FloorView` is `"use client"` — but
  Next SSRs client components, and all 9 published peek names on
  `/maps/oregon/second-floor` appear in the served HTML. CLAUDE.md's
  crawlability rule is **not** violated.
- **Empty `catch {}` blocks (20 of them)** are almost all deliberate — guarding
  `sessionStorage`/`matchMedia` in private mode, or `JSON.parse` of user input.
  Each has a comment. Not a finding.

## 2. Security

### 2.1 Admin server actions have no auth check of their own — MEDIUM
13 of 14 files under `app/admin/(authed)/**/actions.ts` contain zero
`cookieIsValid`/session checks. Only `app/admin/actions.ts` (the login action)
checks anything. All authorisation rests on `middleware.ts:60`, which gates on
`path.startsWith("/admin/")`.

This currently holds, and I verified why: a Next server action POSTs to the URL
of the page that rendered it, and every one of these actions is rendered only
on `/admin/*` pages. I checked all four upload components that live in
`components/` — `DirectGadgetSiteImageUpload`, `GadgetClipUpload`,
`DirectFloorImageUpload`, `DirectVideoUpload` — and each is used exclusively on
an admin page.

**Breaks:** nothing today. It is a latent trap: rendering any of those four
components on a public page would route its action POST through a public URL,
which the middleware does not gate, exposing service-role writes to anyone.
Nothing in the code prevents that.

**Fix:** medium. A shared `await requireAdmin()` at the top of each action makes
the guarantee local instead of depending on where a component happens to be
mounted.

### 2.2 `/api/submissions/upload-url` is unauthenticated and unthrottled — MEDIUM
`app/api/submissions/upload-url/route.ts`

Mints a signed Supabase Storage upload URL for anyone who POSTs a plausible
filename, MIME type and size. It has no rate limit — the 5/hour limit lives
only in `/api/submissions`, which runs *after* the file is already uploaded.

**Breaks:** someone can burn storage by requesting URLs and uploading 50MB files
in a loop. The rows never appear (the insert is limited), but the objects land
in the bucket under `pending/` and nothing sweeps them.

**Fix:** small for the rate limit (reuse `hashIp` from the sibling route);
medium if you also want a cleanup job for orphaned `pending/` objects.

### 2.3 Rate limit silently disables itself without an IP header — SMALL
`app/api/submissions/route.ts:111-122`

`if (ip_hash)` — when `hashIp()` returns null (no `x-forwarded-for` and no
`x-real-ip`), the limit is skipped and the row inserts with `ip_hash = null`.

**Breaks:** Vercel always sets `x-forwarded-for`, so this is not exploitable in
production today. It fails open rather than closed, which is the wrong default
for an abuse guard.

**Fix:** small. Reject when no IP can be determined, or fall back to a
per-session limit.

### 2.4 Things I checked that are fine

- **RLS on `community_submissions` works.** Verified live: anon sees 0 of 1
  rows, anon `INSERT` is blocked with 401. Service role sees everything.
- **`peek_submissions` RLS works.** Anon sees 0 rows of 1.
- **No service-role key reachable from client code.** Zero references to
  `supabaseAdmin` or `SUPABASE_SERVICE_ROLE_KEY` anywhere under `components/`.
- **Stripe webhook verifies its signature** via `constructEvent`
  (`app/api/stripe/webhook/route.ts:34`).
- **Both cron routes check `CRON_SECRET`.**
- **`/api/submissions` validates properly** — MIME allowlist, size cap, link
  host allowlist, path-traversal rejection, and it re-verifies the uploaded
  object rather than trusting the client's declaration.

## 3. Performance

### 3.1 The sequential waterfalls in 1.1 are the biggest LCP item — MEDIUM
Repeated here because it is the single largest server-side cost on the pages
that carry ads. See 1.1.

### 3.2 41 of 46 client components — MEDIUM, needs measurement
Nearly everything in `components/` is `"use client"`. I checked each for hooks
or handlers and **found no trivially convertible ones** — they all use state,
effects or events. So there is no free win here.

Worth a second look anyway: shared first-load JS is 87.2 kB and the heaviest
route (`/gadgets`, 188 kB) is carrying `SubmitSpot`, `LiveStats`, `MapCardImage`
and `SubmitCta` all as client bundles.

**Fix:** medium-to-large, and I would not start it without profiling.

### 3.3 Four raw `<img>` tags without dimensions — SMALL
`components/BirdsEyeWatermark.tsx:46`, `components/MiniMapPicker.tsx:75`,
`app/admin/(authed)/submissions/CommunityCard.tsx:106`, `app/dev/mosaic/page.tsx:83`

Two are admin/dev-only and do not matter. `BirdsEyeWatermark` and
`MiniMapPicker` are public and can shift layout as they load.

**Fix:** small. Add explicit width/height or move to `next/image`.

### 3.4 Things I checked that are fine

- **Map cards reserve space.** `aspect-square` on every card, with a solid
  placeholder, so the grid has zero CLS.
- **The ad script is a single async tag in `<head>`,** untouched.
- **The pin drop and every other animation** are transform/opacity only.
- **`MapCardImage` lazy-loads with a 1000px rootMargin,** so images are usually
  ready before they scroll in.

### 4.2 `DiscordButton` is exported but never rendered — SMALL
`components/DiscordButton.tsx:16`

Its own comment claims it is "used in the site nav (desktop + mobile drawer) and
near the top of the map page". All three are false — the nav Discord button is
hand-rolled markup, the drawer uses a `SECTIONS` menu item, and the map page has
no Discord presence. Only `DiscordBanner` and `DISCORD_INVITE` are used.

Actively misleading, because `SubmitPeekButton` was built to mirror it.

### 4.3 Unreachable roulette sound engine — SMALL
`lib/peek-roulette-wheel.ts`

`RouletteSound` (~80 lines: tick, chime, `AudioContext` handling,
`sessionStorage` persistence) has no reachable caller. Its only importer is
`HomeRouletteLure`, which is itself orphaned (4.1). No `AudioContext` is ever
created, so the runtime cost is zero — it is purely dead weight.

### 4.4 Two unused API routes — SMALL
- `app/api/maps/[slug]/random-peek/route.ts` — zero callers; kept as the
  Roulette rollback path.
- `app/api/maps/[slug]/roulette-peeks/route.ts` — its only caller was
  `HomeRouletteLure`, now orphaned.

Both are live public URLs that hit the database.

### 4.5 `/submit` page has one remaining entry point — SMALL
`app/submit/page.tsx`, ~5.23 kB. The hamburger now points at `/#submit`.
One `href="/submit"` remains. The page is also the only one that shows the new
site-wide banner pointing at a *different* submission form.

### 4.6 No 3D/hologram leftovers
Searched for `hologram`, `webgl`, `Canvas3D`, `three`. Only false positives on
the English word "three". Nothing to clean up.

## 5. Consistency

### 5.1 Map-grid markup duplicated three ways — MEDIUM
`app/page.tsx`, `app/attacking/page.tsx`, `app/gadgets/page.tsx` each hand-roll
the same square map card with its own scrim, ring and label. They have already
drifted: the homepage uses `MapCardLink` with a click-exit animation, the other
two use plain `Link`; `/gadgets` has a blue focus ring and a disabled state that
neither other grid has.

This is a known, documented decision (`app/gadgets/page.tsx:30-34` explains it),
but it is now three copies and the drift is real.

**Fix:** medium. Extracting a shared `MapGrid` means touching the homepage.

### 5.2 Two submission systems side by side — MEDIUM
`peek_submissions` + `/submit` + `app/admin/(authed)/submissions/actions.ts`
versus `community_submissions` + `SubmitSpot` + `community-actions.ts`.

Deliberate, and the admin page now tabs between them. Worth a decision about
retiring the old one rather than carrying both indefinitely.

### 5.3 Two stat-bar components — FINE
`LiveStats` and `MapStats` look like duplicates but are not: different data
shapes, different layouts. Leave them.

## TOP 10

Ranked by what actually costs you something.

1. **Sequential query waterfalls on homepage, map and peek pages** (1.1) —
   the only finding that touches ad revenue and SEO on every request. 17
   queries that could largely run in parallel. *Small fix, real payoff.*

2. **`/api/submissions/upload-url` unthrottled** (2.2) — a stranger can fill
   your Storage bucket with 50MB files today. Nothing sweeps orphans.
   *Small fix.*

3. **Admin actions rely on middleware alone** (2.1) — safe now, but one
   misplaced component turns it into service-role write access from a public
   URL. *Medium fix, removes a whole class of future bug.*

4. **ESLint never configured** — `next lint` cannot run. You are shipping
   without the linter that would have caught several items in this report.
   *Small fix.*

5. **Five queries discarding `error`** (1.2) — silent failures in admin write
   paths, where you are least likely to notice. *Small fix.*

6. **`DiscordButton` dead and its comment lying** (4.2) — it is the reference
   implementation for a button that *is* live. Actively misleading.
   *Small fix.*

7. **Dead roulette + lure cluster** (4.1, 4.3, 4.4) — 2 components, ~80 lines
   of audio engine, 2 public API routes. One cleanup commit. *Small fix.*

8. **Rate limit fails open without an IP header** (2.3) — not exploitable on
   Vercel, but the wrong default. *Small fix.*

9. **Two public `<img>` without dimensions** (3.3) — the only CLS sources I
   found. Everything else reserves space properly. *Small fix.*

10. **Map grid duplicated three ways** (5.1) — the drift is real and will keep
    widening, but nothing is broken. *Medium fix, lowest urgency here.*

**Deliberately not in the list:** the 41 client components (3.2) — I found no
easy conversions and would not touch it without profiling. And the two
submission systems (5.2) — that is a product decision, not a defect.

**What is in good shape:** RLS is correctly configured and I verified it live.
Input validation on the public submission path is genuinely thorough. The
Stripe webhook and both cron routes are properly authenticated. CLS discipline
across map grids and animations is good. TypeScript is clean and the build
passes.
